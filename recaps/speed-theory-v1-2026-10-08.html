Global Router Speed and Theory

A research global router in C++ now routes the largest ISPD 2024 contest design it has tried, mempool_cluster_ranking: 10.6 million nets on a 4113 × 5580 × 10 GCell grid. Its score beats the contest winner by 0.25%. It took 16.9 hours on one core, though, and peaked at 29.4 GB. This page answers four questions about what comes next.

Where the time goes, and what to change first

Are there places in the router that could be refactored or reprioritized to speed up the most complex designs?

Stage times below come from the run's memory log, which stamps each stage line every 15 seconds. The maze-search stages that dominated the earlier ISPD 2008 work took under half an hour here. The time sits in two loops that run after routing is already legal: wirelength recovery and layer assignment.

  1. Give layer assignment a real stop rule

    Under the 2024 score, any round that improves the score by more than 10−6 resets the patience counter, so the loop practically never stops early. First, measure: rerun a mid-size design (bsg_chip_rank or mempool_group_rank) with the per-round trace on and see where the score gain flattens. Then stop on a relative threshold, for example a round that gains less than 0.01% of the score.

  2. Add a gain threshold to wirelength recovery

    Each pass takes 70–85 minutes. The four passes improved wire by 0.36%, 0.04%, 0.003% and 0.0002%. Stopping when a pass gains under about 0.01% removes the last two passes at essentially no quality cost.

  3. Run those two loops on many cores

    Both work net by net and suit the batched scheme the project already built for the 2008 benchmarks: search in parallel against a snapshot, commit in a fixed order, re-search only the conflicts. One change is needed at this scale. The earlier version gave every worker its own copy of the usage arrays, and a 3D copy here is about 0.9 GB. Workers should instead read one shared snapshot and keep only their own changes.

Estimate, not yet measured: stop rules alone could bring this design to about 6–8 hours; adding about 10 threads on the two loops, to about 2–3 hours. That would still be far from the contest winners' 2–5 minutes, so the score is competitive but the runtime is not. Next in line after that are the pattern stage (55 min) and layer assignment round 0, which also adds 10.8 GB of memory.

A mathematical model of the routers

How would you model the router and the routers tried so far, what could that show, and could it suggest significant improvements?

The problem underneath

Every router in this project is a heuristic for the same optimization: give each net a tree connecting its pins, and charge each GCell for how much demand lands on it.

minimize Σnets i cost(treei) + ΣGCells g fg(usageg) where usageg = demand from every tree crossing g, including via demand

In the 2024 contest score, f grows exponentially with demand over capacity. That makes it convex, and a convex cost lets the relaxed problem be treated with standard optimization theory: it has duals, lower bounds and convergence measures.

Sorting the project's measured results by which of the four choices they changed shows where the large gains came from:

Price update

  1. Permanent congestion history −0.5 to −2.7%
  2. History that can relax again another −0.6 to −1.4%
  3. NTHU present-demand price + history, with keep-every-reroute −86.5% overflow either half alone made things worse

Oracle

  1. Maze growth from all built wire, not a fixed tree −21 to −37% overflow
  2. Search box 6 tiles → growing to 200 −60% overflow
  3. Per-tile layer choice, NTHU-style adaptec1 to zero

Acceptance

  1. Revert if worse: essential under an ever-rising price
  2. Keep every reroute: essential under present-demand pricing part of −86.5%

Schedule

  1. Net-ordering experiments low single digits, one regression
  2. Batched pattern stage −37% runtime
  3. Parallel batches, 8–10 threads 1.6–2.4× faster

The theory explains the pattern. Price-update methods converge only if the per-net search really finds that net's cheapest route at the current prices. A 6-tile search box or a fixed tree is a restricted search, and no price formula makes up for it. That is why the biggest wins came from widening the oracle, and it says where to look next: wherever the search is still restricted.

  • Layer assignment works on a fixed 2D tree.
  • The 3D passes try only L and Z shapes.
  • The 2D stage never sees layer assignment's prices; the two stages run in sequence with no feedback.

What a model would add

Where headroom is

A certified lower bound on the score

Because the cost is convex, a Lagrangian dual gives a provable floor on the achievable score, per design and per component (wire, vias, overflow). The project already did this for 2008 overflow: a cut bound proved most of newblue3's residue is forced for any router. On designs within 0.25% of the contest winner, a bound says whether a 25%-scale gain exists anywhere.

When to stop

A duality gap every round

A Frank-Wolfe-style round yields a convergence gap at almost no extra cost. That is the stopping signal layer assignment lacks today, and it also suggests step sizes in place of keeping every reroute.

What to build

Finding the restricted search

Comparing each stage's routes with what an unrestricted search would pick shows which restriction binds. The project's box-binding test (does a net's search actually hit its box edge?) is a small instance of this idea.

Before a 21 GB download

Scaling laws

Fitting time and memory per stage across the three MemPool sizes (tile, group, cluster) would predict tera_cluster, the largest contest design, before downloading it. A rough guess is about 5× the cluster design, which would not fit this machine.

Could it lead to significant improvements? Indirectly, yes. The bound shows whether headroom exists, the gap gives better stop rules, and locating restricted searches points at the next structural change, which is what every big win so far has been. It will not replace experiments: the project's record shows measured results beating reasoned guesses again and again.

Running on GitHub's cloud

Is now a good time to try a GitHub cloud run on some of the benchmarks?

Not yet for the large designs. GitHub Actions jobs are capped at 6 hours each, and the repository is private, which on the free plan means small runners and 2,000 minutes a month. The project's last CI runs had used up those minutes.

Suggested order of work

  1. One traced run of a mid-size design to measure per-round score gains in layer assignment.
  2. Stop rules for layer assignment and wirelength recovery, checked against the current scores on every 2024 design.
  3. Threads for those two loops, with a shared snapshot instead of per-worker copies.
  4. In parallel, since it needs no machine time: a lower bound on the 2024 score, starting with one mid-size design.
  5. Cloud runs once a cluster design fits in 6 hours, or a rented machine sooner if waiting costs more than renting.
