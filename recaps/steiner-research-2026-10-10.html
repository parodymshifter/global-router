Steiner Research Roadmap

Every net in a global router is a Steiner tree, and the shape of that tree decides wire, vias, congestion and delay at once. This page collects what has been published since 2024 on building trees that balance wire length against capacity, path length, delay and proximity to obstacles. It then sorts those ideas into a plan for this router, by what the router's own measurements say each one could buy.

Delay-driven rectilinear Steiner trees (CUHK)2025 Starts from the observation that shallow-light trees (SALT) balance wire and path length well but not real delay; adds delay-driven edge shifting. Lowest total delay among compared methods, competitive wiremedium

NeuralSteiner2024 A network predicts Steiner points from the overflow map, then a graph step connects them: the tree is shaped around congestion instead of drawn on empty space. How these fit this router

The plan, ordered by what the router's own measurements say each step can buy

Three facts set the order. Tree length alone has little room: our trees are within 0.2–0.8% of a strong reference. The score's movable part is congestion that never quite overflows: 71M of cost on busy but legal GCells. And runtime is still 2.4× the winner's on the hidden cluster, with threads earning only 1.7–2.5× in two big stages.

Every experiment follows the project's rules. One design screens first, then all 13. Scores are checked by the official evaluator. Changes meant to be exact must be byte-identical at 1 and 8 threads. Score changes inside ±0.02% count as noise, and a change is adopted only if it holds on every design.

Passes 1 and 2 re-examine all 9.6M nets, but only 0.74M and 0.31M change. A net whose surroundings have not changed since it last kept its route would choose the same again, so it can be skipped. Also: remove the scheduler's shared lock on every finished task, and build its dependency graph in parallel.

Pattern stage: the single-threaded parts

Threads give this stage only 1.7×. A traced run found that solving pieces takes 177 of its 240 s. In the 29 later rounds, each batch holds about 65 pieces, under the size where solving goes parallel. The threads sit idle 87% of the time. Pieces in a batch never overlap, so each piece can wait only for the earlier pieces that overlap it, as layer assignment's pieces already do.

Cost-distance trees as the per-net solver

The project's founding idea is a Lagrangian loop in which each net solves a minimum-cost Steiner tree under its own shaped costs. Cost-distance trees are exactly that solver with delay added: congestion prices plus each sink's criticality times its path delay.

Not now

and why
  • Learned Steiner trees (GAT-Steiner, NeuroSteiner). Our trees are already near optimal in length, and a network would add a GPU dependency and break the same-answer-at-any-thread-count rule for at most a few tenths of a percent.
  • A GPU tree builder (SFP, GPU FLUTE). Tree building now takes about 16 s of the public cluster's 658 s on 8 threads. SFP is the right choice if trees ever become a bottleneck again, because it is deterministic.
  • Learned batching (GANGR). Part 119's tile spreading already removed the wasted work it targets; the slow tier is now 7% of the hidden cluster's run.
  • Language-model tuning (AlphaRoute). Its results use a different score and are not comparable; the project's record favors structural changes over parameter tuning.
